# E2EE flow — Plan 1/3: Backend foundation (schema, types, quota/links helpers)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the Prisma schema migration and shared-type changes the rest of the E2EE
send/receive redesign depends on, and update the existing quota/link helper functions to work
against the new `Drop` columns without changing their observable behavior for the parts that
aren't changing.

**Architecture:** `Drop.status` (a single 4-value string) splits into four independent columns:
`fileUploadStatus` (internal transfer bookkeeping, same CAS role `status` played for `uploads.ts`),
`deliveryStatus`/`messageEnvelopeStatus`/`fileEnvelopeStatus` (display-level, written by plan 2's
endpoints, read by spec 5 later — this plan only adds the columns and their defaults). `message`,
`fileName`, `mimeType` move from plaintext columns to encrypted blob + nonce pairs (content itself
is written by plan 2/3; this plan only adds the columns). `Link.recipientPublicKey` becomes
nullable (unclaimed state) and `Link.retentionDays` becomes non-null (always set at creation).

**Tech Stack:** Prisma (Postgres), TypeScript, existing `@e2ee-drop/shared` package for cross-package types.

**Spec:** `docs/superpowers/specs/2026-09-26-e2ee-send-receive-flow-design.md`

**Plan sequence:** This is plan 1 of 3. Plan 2 (`2026-09-26-e2ee-flow-2-backend-endpoints.md`)
adds/rewrites the API routes on top of this foundation. Plan 3
(`2026-09-26-e2ee-flow-3-frontend.md`) rebuilds the frontend against plan 2's API. Do not start
plan 2 until this plan's migration is applied and `pnpm -r test` passes.

## Global Constraints

- Every DB write that currently uses `updateMany` for compare-and-swap (CAS) must keep that
  pattern — never replace a CAS `updateMany` with a read-then-`update`, which reintroduces the race
  the original code was written to prevent.
- Lock ordering documented in `apps/api/src/lib/quota.ts` (User row → Link row → Drop row(s)) must
  not change.
- No `--no-verify`, no skipped migrations. Use `prisma migrate dev`, never `db push`, matching the
  existing migration history in `packages/db/prisma/migrations/`.
- This is a breaking, lossy schema change for any pre-existing `Drop` rows — see Task 1's note.
  Flagged for the human reviewer, not something to route around.

## Review Focus

- **A `Drop` row created before this migration, still `"uploading"` at migration time**: it has no
  `fileUploadStatus`/`encryptedMetadata`/etc. — the migration must give it *some* valid values (not
  leave the table in a state the app's own TypeScript types say is impossible) rather than silently
  producing NULLs in NOT NULL columns and failing the migration outright.
- **`Link.retentionDays` NOT NULL migration on existing rows**: every existing `Link` row has
  `retentionDays IS NULL` today (it was always optional) — a blind `ALTER COLUMN ... SET NOT NULL`
  fails immediately on any real database with existing rows. Must backfill first.
- **`Link.recipientPublicKey` losing NOT NULL**: this is a *relaxation*, not a tightening, so it's
  safe for existing rows — but every existing call site that reads `link.recipientPublicKey`
  assuming it's a `string` (not `string | null`) will now fail to typecheck, and must be found and
  fixed, not left to surface as a runtime crash later.
- **`isChargedStatus` boundary condition**: today, "charged" means `status !== "uploading"` — i.e.
  every one of `uploaded`/`downloading`/`downloaded` counts as charged. The new `fileUploadStatus`
  only has `reserved`/`uploading`/`complete` — a careless port could write `!== "uploading"`, which
  would make `reserved` count as charged too (wrong: nothing is charged before `complete`).
- **`transitionDropStatus`'s remaining callers**: this plan narrows the function to
  `fileUploadStatus`; anything still calling it expecting to transition the old `status` values
  (e.g. `"uploaded"` → `"downloading"`) belongs to plan 2's rewrite of `downloads.ts`, not here —
  leaving a stale caller uncompiled is the correct outcome for this plan (plan 2 fixes it), but a
  caller that compiles by accident (e.g. because `"uploading"` happens to also appear in the old
  status enum) must be checked for explicitly.

Note the deliberate deviation from the spec doc's literal Prisma snippet: `fileUploadStatus`
defaults to `"uploading"`, not `"reserved"`. Grounding against `apps/api/src/routes/uploads.ts`
shows every code path that will create a `Drop` in plan 2 does so once a real upload attempt has
begun (mirroring today's `status: "uploading"` on creation) — there is no code path in plans 1–3
that ever writes `"reserved"`. It stays in the *value space* (documented below) because spec 2 is
expected to use it for an eager, pre-upload-url tracking row; nothing in this plan or plan 2 writes
or reads it. Document this in the migration's SQL comment and in the schema:

```prisma
  // fileUploadStatus: "uploading" | "complete" — internal transfer bookkeeping, mirrors the old
  // Drop.status's role in uploads.ts's CAS logic. A third value, "reserved", is reserved for
  // spec 2's eager pre-upload tracking (not written or read anywhere in this plan or plan 2).
  fileUploadStatus     String  @default("uploading")
```

- [ ] **Step 3: Hand-edit the generated migration SQL**

Open the new `packages/db/prisma/migrations/<timestamp>_e2ee_flow_envelopes/migration.sql`. Prisma
will have generated, in some order, drops/adds/renames for the changed columns and constraint
changes for `retentionDays`/`recipientPublicKey`. Rewrite it (order matters) to:

```sql
-- 1. Add all new nullable columns first (never fails on existing rows).
ALTER TABLE "Link" ADD COLUMN "ownerNote" TEXT;
ALTER TABLE "User" ADD COLUMN "showEmailOnPublicProfile" BOOLEAN NOT NULL DEFAULT false;

ALTER TABLE "Drop" ADD COLUMN "archiveNonce" TEXT;
ALTER TABLE "Drop" ADD COLUMN "encryptedMessage" TEXT;
ALTER TABLE "Drop" ADD COLUMN "messageNonce" TEXT;
ALTER TABLE "Drop" ADD COLUMN "messageRevealedAt" TIMESTAMP(3);
ALTER TABLE "Drop" ADD COLUMN "encryptedMetadata" TEXT;
ALTER TABLE "Drop" ADD COLUMN "metadataNonce" TEXT;
ALTER TABLE "Drop" ADD COLUMN "fileUploadStatus" TEXT NOT NULL DEFAULT 'uploading';
ALTER TABLE "Drop" ADD COLUMN "deliveryStatus" TEXT NOT NULL DEFAULT 'sender_opened';
ALTER TABLE "Drop" ADD COLUMN "messageEnvelopeStatus" TEXT NOT NULL DEFAULT 'sealed';
ALTER TABLE "Drop" ADD COLUMN "fileEnvelopeStatus" TEXT NOT NULL DEFAULT 'sealed';
ALTER TABLE "Drop" ADD COLUMN "contentDeletedAt" TIMESTAMP(3);

-- 2. Backfill from the old columns where a like-for-like mapping exists. Every existing Drop
--    row predates the three-envelope split, so its "message"/"fileName"/"mimeType" were always
--    plaintext — they CANNOT be retroactively encrypted (no server-held key ever existed for
--    them; that's the point of E2EE). This backfill preserves what the old columns already
--    guaranteed (upload/download progress) and deliberately drops what it cannot: any
--    pre-migration message/filename/mimetype is lost, not smuggled into the new encrypted
--    columns unencrypted.
UPDATE "Drop" SET "archiveNonce" = "nonce";
UPDATE "Drop" SET "fileUploadStatus" = CASE
  WHEN "status" = 'uploading' THEN 'uploading'
  ELSE 'complete'
END;
-- Old "downloading"/"downloaded" drops already left the upload phase; map to a display status
-- consistent with that so a drop that was already fully delivered doesn't regress to
-- "sender_opened" post-migration.
UPDATE "Drop" SET "deliveryStatus" = CASE
  WHEN "status" = 'uploading' THEN 'sender_opened'
  WHEN "status" = 'uploaded' THEN 'sent'
  ELSE 'delivered'
END;
UPDATE "Drop" SET "fileEnvelopeStatus" = CASE
  WHEN "status" = 'downloaded' THEN 'delivered'
  ELSE 'sealed'
END;
-- No pre-existing message content survives (see comment above) — mark any row that HAD a
-- message as already-revealed-and-gone rather than silently pretending it never had one.
UPDATE "Drop" SET "messageEnvelopeStatus" = 'delivered', "messageRevealedAt" = "createdAt"
  WHERE "message" IS NOT NULL;
-- Placeholder metadata for pre-migration rows: NOT NULL columns need a value, and there is no
-- recipient key on hand at migration time to encrypt the old plaintext fileName into
-- encryptedMetadata. Empty-envelope placeholders that will simply fail to decrypt cleanly
-- (a receiver sees "unable to read metadata" for these, not a 500) rather than a fabricated
-- ciphertext that looks legitimate.
UPDATE "Drop" SET "encryptedMetadata" = '', "metadataNonce" = '';

-- 3. Now that every row has a value, make the columns NOT NULL.
ALTER TABLE "Drop" ALTER COLUMN "archiveNonce" SET NOT NULL;
ALTER TABLE "Drop" ALTER COLUMN "encryptedMetadata" SET NOT NULL;
ALTER TABLE "Drop" ALTER COLUMN "metadataNonce" SET NOT NULL;

-- 4. Drop the old columns.
ALTER TABLE "Drop" DROP COLUMN "nonce";
ALTER TABLE "Drop" DROP COLUMN "fileName";
ALTER TABLE "Drop" DROP COLUMN "mimeType";
ALTER TABLE "Drop" DROP COLUMN "message";
ALTER TABLE "Drop" DROP COLUMN "status";

-- 5. Link.retentionDays: backfill from the existing env default (7, matching today's
--    DROP_RETENTION_DAYS default in apps/api/src/env.ts) before tightening to NOT NULL.
UPDATE "Link" SET "retentionDays" = 7 WHERE "retentionDays" IS NULL;
ALTER TABLE "Link" ALTER COLUMN "retentionDays" SET NOT NULL;

-- 6. Link.recipientPublicKey: relaxing NOT NULL is always safe on existing rows.
ALTER TABLE "Link" ALTER COLUMN "recipientPublicKey" DROP NOT NULL;
```

async function reservedUploadBytes(
  tx: Prisma.TransactionClient,
  userId: string,
  senderKey?: string
): Promise<{ bytes: bigint; oldestCreatedAt: Date | null }> {
  const { _sum, _count, _min } = await tx.drop.aggregate({
    where: {
      fileUploadStatus: "uploading",
      createdAt: { gt: reservationCutoff() },
      link: { ownerId: userId },
      ...(senderKey === undefined ? {} : { reservationSenderKey: senderKey }),
    },
    _sum: { fileSize: true },
    _count: { _all: true },
    _min: { createdAt: true },
  });
  return {
    bytes: BigInt(_sum.fileSize ?? 0) + BigInt(_count._all) * BigInt(NACL_BOX_OVERHEAD_BYTES),
    oldestCreatedAt: _min.createdAt,
  };
}
